The Trunk That Wasn't: three records, one network, no reconciliation

A form that looks filled in is not proof that anything was saved. The device’s output is.

What happened

This is a training lab, on a simulated network. It is not client work. The lab is Troubleshooting Fundamentals, Phase 1.3 from Witty Networks. The diagrams below are my own.

Five devices, one network: two switches (SW1 and SW2) and three computers (Host A, B and C). The ticket: Host C can’t reach Hosts A and B.

Before. The link between the switches was set up differently at each end, and Host B had no address.

Before I touched anything, the lab’s own diagram was already wrong. It listed Host C as 182.168.1.4. The device itself said 192.168.1.4. The record was wrong before work started.

The technician’s view

There were two faults.

1. The link between the switches. On SW1 the connecting port was a trunk, a link that carries several networks at once and labels each message with its network. On SW2 the same link was a plain access port that expects no labels. The two ends disagreed, so traffic from Host C couldn’t cross. SW1’s port description even said Trunk_to_SW2, which recorded what the link was meant to be. The fix, written out and reviewed before typing, at SW2(config-if)#: switchport mode trunk. After it, Host A could reach Host C.

2. Host B. With the link fixed, I ruled things out one at a time: the link (A to C now worked across it), the network settings on both switches, Host C, and Host B’s switch port. The only suspect left was Host B. It had no address at all.

The near miss. My first fix on Host B didn’t take. The settings panel showed grey placeholder text (192.0.2.x) that looked like saved values. Only ipconfig, the computer’s own report, showed that nothing had changed. The second time I gave Host B 192.168.1.3 with mask 255.255.255.0, checked it on the device, and Host C reached Host B.

I left the gateway blank on purpose. There’s no router in this network and all the computers share one subnet. A gateway of .1 would have passed the ping test while pointing at a device that doesn’t exist.

After. Both ends of the link agree, and Host B is on the network.

Where this happens for real

An illustration of the same faults in a real setting. It is not a real incident.

Picture a small clinic with the same five devices. SW1 sits at the front desk, with the reception computer (Host A) and the nurse station (Host B). SW2 sits in the records room, with the server that holds patient records (Host C).

  • The link fault. The records-room switch is replaced in a hurry, and its end of the link isn’t set up the way the front-desk end expects. Every light is green and the cable is fine, but the front desk can’t open a single patient record.
  • The missing address. A new nurse-station computer goes in. The settings screen looks filled in, so everyone assumes it’s on the network. It isn’t.

Nothing is “down” in a way an alarm would catch. Patients wait while staff fall back to paper. Then the workarounds start: records copied to USB sticks, a phone used as a hotspot. That’s how a configuration gap becomes a privacy and security problem.

The architect’s view

From here on I’m asking: what if this were a real network?

Three records described this network: the diagram, the port descriptions, and the device settings themselves. Nothing compared them. Each fault was a gap between a record and reality. There was no step that checked a device against its design after a change, and no check that a device was set up before it went into service.

# Finding Pillar Lifecycle Lesson
1 The diagram and the device disagreed on Host C’s address Metadata Operate Reality wins; the record is the finding
2 Placeholder text read as saved settings Metadata Maintain Evidence over assertion
3 A gateway pointing at a device that doesn’t exist (proposed, caught at review) Metadata Maintain A ghost record
4 SW2 had drifted from the design recorded in SW1’s description; the two ends use different description formats Metadata Operate Configuration drift
5 The lab’s checker passed the outcome without checking the settings Assurance Maintain Performative compliance

The control

NCV-1: Network Change Verification. What it requires:

  1. Every change is written out, with the prompt it will be typed at, and reviewed before it’s typed.
  2. Before and after evidence comes from the device itself, with the device name visible. Forms and diagrams don’t count.
  3. After a change, both ends of a link are checked against the design record (show run int).
  4. Every value in a configuration must name something that exists: an address, a network, a gateway.
  5. Any gap between a record and a device is logged as a finding. The record is corrected, unless the device breaks the design.

How to prove it works

In this lab: the port status on both switches, the settings of the link port on both ends, ipconfig on Host B before and after, a ping on each path, then the lab’s checker.

On a real network: a scheduled export of every device’s settings, compared against the register and the diagram. Any mismatch is a finding. Planned, not built yet: a tool that reads a network diagram into a register, which gives that comparison its starting point.

Takeaway

On the network In asset governance
Network diagram The asset register
Port description Metadata that records design intent
show run / ipconfig Inspecting the asset itself, the physical truth
An unsaved form field A record entry with no evidence behind it
The lab checker An outcome test, not a configuration audit

A technical fix solved the ticket. A control that compares records with devices solves the class of failure.
